# Daemon-owned pairing session design

Status: Implementation design under the approved desktop product scope; transport implementation in progress. No installed-host or complete-pairing claim.

Date: 2026-09-06

## Product boundary

Both Desktop and the CLI initiate and observe the same local daemon-owned pairing session. The daemon owns credentials and all network activity. A local-only installation remains usable without pairing. Pairing establishes a peer identity, never blanket permission to execute recipes or access protected operating-system resources.

This design resolves the source assessment in `2026-09-06-onboarding-pairing-gap-assessment.md`. It does not reuse the legacy in-band code echo. Its TLS foundation is specified in `../plans/2026-09-06-ephemeral-pairing-tls.md`; that adapter alone is not this whole feature.

## Chosen trust ceremony

Use a short-lived, high-entropy invitation carrying the controller's exact public certificate. The user transfers it directly from the intended controller's display by QR or copy/paste. It contains no private key. Copy/paste alone is not authenticated: before confirmation the user must compare the controller certificate fingerprint with the fingerprint independently displayed by the controller, not merely approve values supplied by the invitation.

After candidate authentication, the controller similarly compares the candidate fingerprint with the candidate device's own local identity display. Both devices display both full SHA-256 fingerprints, stable certificate identities, readable names clearly marked as labels, requested roles and intended connection. No truncated fingerprint or matching display name is accepted as proof. The primary action states that the fingerprints match; reject/cancel remains equally accessible. A direct QR transfer from a physically verified controller screen can convey the controller pin, but does not remove the controller's candidate confirmation.

The invitation secret is 128 random bits, generated by the daemon. It is a bearer invitation, not a six-digit password. The UI offers copy/scan actions rather than requiring manual transcription. It must never appear in ordinary logs, audit records, status responses or diagnostics. Only the initiating authorized local client receives the invitation; subsequent status reads expose a session identifier and remaining time, not its secret.

## Wire separation and proof of key possession

The temporary pairing listener does not run the normal registry RPC dispatcher. It binds an explicitly selected numeric private or loopback address after validation. Wildcard/public/unsupported addresses are rejected before binding or identity creation.

The connector first supplies only its public certificate in a length-bounded preface. That certificate creates connection-local memory only: no trust write, active-candidate replacement, invitation consumption or user prompt. The controller's TLS root for this connection is exactly that certificate; the connector's TLS root is exactly the controller certificate from the invitation. Standard TLS 1.3 client and server certificate verification and CertificateVerify establish possession of the respective private keys. Both sides additionally require exact presented leaf DER and pairing ALPN `devicelane-pairing/1`.

Only after those checks does the connector send the invitation secret and its proposed session tuple through TLS. The controller validates the tuple against its own active session. A wrong token or unauthenticated preface cannot reserve the candidate or consume the invitation. A legitimate token-bearing candidate is admitted at most once; changing that candidate requires cancelling and creating a new invitation. In this first session protocol, loss of the authenticated channel after token verification terminates a pre-persistence session, even for the same candidate. It requires a fresh local invitation and fresh confirmations; old peer-confirmation messages are never imported into a new channel. If persistence has already begun, channel loss produces partial repair and reconciliation, not an automatic new pairing or inferred rollback.

The later session listener must enforce a bounded preface without buffering away initial TLS bytes. Use an exact length-delimited read; do not wrap a buffered preface reader around a socket and discard unread buffered bytes before the TLS handoff.

## Authoritative tuple and expiry

The controller creates and retains the authoritative invitation version, random session ID, secret, actual bound pairing address, intended normal registry address, controller certificate/identity, allowed role and monotonic expiry. Client-supplied fields cannot extend time or replace any of them. Canonical numeric addresses are compared, including IPv6 scope where applicable; hostname/DNS resolution is not part of first-trust selection.

Each side's local confirmation binds the same immutable tuple: protocol version, session ID, both exact certificate digests, both certificate identities, both roles, canonical pairing endpoint and canonical intended registry endpoint. Both endpoint values are shown in the confirmation details and included identically in session validation, approval binding and audit metadata. A received peer confirmation is evidence about the peer only; it never substitutes for local OS-authenticated approval.

The entire invitation lasts at most two minutes from controller creation. The connector also applies its own two-minute upper bound from import, without treating the imported TTL as authority over the controller. Restart invalidates pending sessions. Every blocking read/write is bounded by the remaining absolute session time and a shorter per-operation timeout; a stream of partial bytes cannot extend the deadline. At most one session and four simultaneous pre-authentication connections are allowed per daemon, with at most sixteen connection attempts per invitation. Exhaustion closes the invitation with an explicit retryable status requiring a new local start action.

## State transitions

| State | Entry evidence | Allowed next actions |
| --- | --- | --- |
| Invitation active | Explicit authenticated local start; validated bind and private in-memory invitation | Accept bounded candidate prefaces, cancel, expire |
| Pinned TLS | Successful mutual key proof, exact leaf pins and pairing ALPN | Verify secret and authoritative tuple; otherwise close connection |
| Candidate pending | Secret/tuple verified; immutable candidate recorded | Display both identities; local reject/confirm, peer reject, cancel, expire |
| Locally confirmed | Exact fresh local approval for the tuple | Wait for peer confirmation; reject/cancel/expire before persistence |
| Both confirmed | Exact local approval and matching peer confirmation on the pinned channel | Revalidate current revocation/trust/session state; begin audited persistence |
| Persisting | Audit attempt committed before mutation; exact tuple fenced against replacement | Commit local trust/configuration, record outcome, reconcile errors |
| Verifying connection | Local persistence outcome verified and exchanged with peer | Fresh normal mTLS connection and harmless authorized inventory check |
| Active | Both sides report the same committed tuple and post-commit check succeeds | Close pairing listener; normal policy-controlled mesh use |
| Partial repair | Any post-mutation uncertain, one-sided or failed outcome | Show exact safe repair state; no automatic replacement or false rollback |
| Cancelled / expired / rejected / failed | Explicit terminal decision or bounded pre-commit failure | Close listener and streams; remove in-memory secret/candidate; start a new session only by local action |

Pinned TLS is connection-local, not globally paired. An adapter created from a revocation snapshot must be invalidated if its daemon later revokes that peer or changes identity. Revalidate immediately before persistence as well. Normal RPC authorization never consults ephemeral pairing roots.

## Persistence and recovery

Distributed atomicity is not assumed. Each daemon serializes its own exact trust/configuration mutation, audits before mutation, and reconciles actual disk state after any write error. Existing conflicting trust is never overwritten; revoked identities remain rejected. An identical existing trusted certificate is an explicit already-paired condition, not a new mutation disguised as first pairing.

An audit failure before mutation leaves prior trust and configuration unchanged. After mutation begins, failures may have changed disk state: report that uncertainty and fence new remote work until reconciliation. Never delete a possibly committed trust record as an inferred rollback. Cancelling during persistence means stop further work and inspect the reached state, not promise that nothing happened.

Crash recovery must use daemon-owned, private transaction metadata bound to the exact tuple and independently verified trust/configuration bytes. It may reconcile an already authorized local outcome, but cannot revive an expired invitation, create a new peer decision, or accept a replacement certificate. Local persisted trust alone is insufficient for an `Active` UI state. Recovery needs a fresh normal mTLS check and an honest peer-outcome exchange; otherwise show partial repair.

This requires crash-safe persistence beyond the current `write_secret` implementation. Session integration must not claim durability by merely calling that truncating write helper. Identity migration and protected OS storage remain separate required product work and must preserve existing credentials.

## Local API and interface behavior

### Verified runtime integration prerequisite

The current `devicelane-service` does not implement a registry server merely by selecting `--role registry`: `run` initializes local dashboard state, starts an inventory observer and serves local IPC. Its parsed `agent_peer` is not used to start a remote worker. Separately, `scripts/setup-windows.ps1` installs a `mesh-registry` process with its own identity directory; `desktop/scripts/stage-sidecar.mjs` bundles only `devicelane-service` and `devicelane`.

Consequently, a new service-owned invitation must not claim to authenticate the existing separately keyed registry endpoint. Before create-mesh can be exposed as working, controller runtime integration must prove that the advertised normal endpoint presents the exact confirmed controller certificate and runs the intended registry role under daemon lifecycle ownership. A role label or successful local IPC response is not evidence of that integration. Preserve the existing registry identity and configuration; no implicit key copy, replacement, trust expansion or forced migration is permitted. The two-daemon/post-commit test below must cover this real endpoint identity, not a separately pretrusted fixture substituted for the daemon.

Add typed session start/import/status/cancel/confirm operations to authenticated local IPC. No operation accepts a credential path, arbitrary executable, environment or raw shell. The daemon derives the stable local identity from its own validated certificate; readable host labels are separate settings. Capability advertisement distinguishes pairing support from ordinary connection settings so older clients fail explicitly rather than silently invoking legacy pairing.

The wizard contains local-only/create-mesh/join choices, name and autostart settings, toolchain/permission checks, invitation transfer, independent fingerprint comparison, progress and the resulting rules. It polls session status without holding an IPC lock across network work. Closing the dialog does not undo a sent confirmation; cancelling is an explicit daemon request. Pending, expired, denied and partial outcomes have distinct text and actions. Keyboard focus, screen-reader labels and non-color status cues are mandatory.

CLI commands follow the same states and exact approval contract. Automation may observe/provide a prepared invitation, but does not fabricate the required target confirmation or bypass OS permission prompts. A managed unattended enrollment workflow is not introduced by this feature.

## Required verification

- Real TLS tests verify candidate-only roots, exact client/server pins including CA descendants, private-key proof, pairing ALPN and byte-preserved ordinary trust. These prove the adapter only.
- Session tests cover complete invitation substitution, wrong/expired/replayed tokens, altered role/endpoint/identity, candidate changes after either confirmation, unauthorized IPC and ordinary RPC on the pairing listener.
- Deadline tests include an idle listener, junk first connector, slow partial preface/TLS/message reads, oversized/malformed input, attempt exhaustion, cancellation and daemon restart. A junk connector cannot permanently consume an otherwise valid invitation before token verification, within the explicit resource limits.
- Persistence fault tests independently fail audit, trust, configuration and outcome writes on each daemon, including crashes and ambiguous write completion. Assert unchanged prior state before mutation and truthful partial states afterward.
- Two actual daemon processes complete confirmation, persist, restart and perform normal authenticated inventory; normal RPC stays unavailable to a candidate before confirmation.
- Native Windows and the real Mac complete the wizard and CLI-equivalent workflow, then restart/autostart and execute a policy-controlled remote job. Fixture tools and hosted macOS CI do not satisfy these installed-host gates.

## Review record

Independent bounded design review accepted standard mTLS plus an independently conveyed exact certificate pin in principle. It required genuine cross-device comparison, server-authoritative session metadata, exact leaf checks, no pre-authentication side effects and explicit partial-commit states. A second review confirmed those five blockers are resolved by this design and requested explicit post-token channel-loss behavior and identical endpoint binding. Both clarifications are incorporated above. The final wire/state/persistence implementation still requires independent review and tests; this is not a security certification.
